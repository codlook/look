# LOOK Benchmark Protocol

This document **locks** how LOOK is measured against Node.js and PHP so that every future
optimization can be checked against a fixed baseline with the same rules. Nothing here is a
marketing claim — it is the method. Raw numbers live in `docs/look.codlook.com/benchmarks.html`
and are regenerated by re-running this suite; this file defines *how* they are produced.

> **Rule zero — lock before you optimize.** The suite is frozen *before* CPU work starts, so a
> change that claims "2× faster arithmetic" must show it on this exact harness or it did not happen.

## Honest framing (read this first)

We do **not** publish a single composite score. A weighted score invites the fair rebuttal
"you picked the weights." We publish raw per-test numbers and one honest sentence:

> **LOOK wins on memory efficiency, sustained concurrency, tail-latency stability, and
> non-keep-alive throughput. Node wins on JIT-optimized CPU microbenchmarks and low-load
> keep-alive throughput. PHP (with OPcache + JIT + FPM) is competitive on CPU and trails on
> memory and tail latency.**

When a CPU optimization lands, we re-run and update the numbers — including the ones where we
still trail. Showing `130× → 12× → 4× → 1.8×` over time, **without a JIT**, is the story; hiding
the tests we lose is not.

LOOK is its own web language — not a replacement for any of these. The comparisons exist to
locate LOOK's cost, not to frame an "X vs LOOK" contest.

## Fairness lock (non-negotiable — the credibility of the whole suite)

Crippling a competitor to win is worse than losing a test. All three run in a realistic
production configuration:

| Runtime | Version (pin exact patch at run time) | Configuration |
| --- | --- | --- |
| **Node.js** | 22.x LTS | default production run (`node app.js`); **JIT ON** (never `--jitless`), cluster only where the test explicitly measures multi-process |
| **PHP** | 8.3.x | **OPcache ON + JIT ON** (`opcache.enable_cli=1`, `opcache.jit=tracing`, `opcache.jit_buffer_size=128M`); FPM for web tests, CLI for language-core |
| **LOOK** | build stamped via `--version` (git sha) | bytecode VM default (`LOOK_CLI_VM=1`), `lk-fcgi` for web |

For web tests, an optional secondary table may show **PHP JIT ON vs OFF** and **Node default** side
by side — but the headline PHP/Node columns are always the production-default config a real user runs.

## Environment lock

Every test runs in the **same** container shape; the load generator runs in a **separate**
container so its CPU never steals from the server under test.

- Docker, `--cpus=2 --memory=4g`, same base image family across runtimes.
- Load generator (`wrk` / `ab`): separate container, uncapped, so it is never the bottleneck.
- Warm-up before every timed run; **best-of-3**, report the best (least-noisy) run.
- **Hygiene rule 9 is mandatory:** under any CPU quota, read `/sys/fs/cgroup/cpu.stat` before
  trusting tail latency — `nr_throttled > 0` under load means the numbers include CFS scheduler
  throttling, not server latency. Set worker threads ≤ the quota and re-measure. (This is the
  bug that produced the phantom "40ms p99"; see `cpp/bench/micro/SPEC.md`.)

Record at run time and paste into the results page: hardware, OS, kernel, Docker version, CPU,
RAM, the three runtime versions, compiler flags, Node flags, PHP flags, DB version, DB schema,
concurrency, duration, warm-up, run count, load generator.

## The suite (v1 — 15 tests, frozen)

Kept deliberately small; too many tests drown the reader. Each reports only:
`throughput · p50 · p95 · p99 · RSS · CPU · errors`.

### World 1 — Pure language core (no HTTP) → `cpp/bench/micro/`

Governed by `cpp/bench/micro/SPEC.md` (17 benchmarks, integer-checksum equivalence, 9 hygiene
rules). Node may win here — that is expected and published as-is.

| # | Test | Measures |
| --- | --- | --- |
| 1 | `int_arith` | integer CPU / VM dispatch |
| 2 | `fn_call` + `nested_fn` + `recursion` | VM call overhead |
| 3 | `string_concat` / `string_search` / `string_slice` | string runtime |
| 4 | `array_create_iterate` / `array_push_pop` | array data structure |
| 5 | `assoc_access` / `object_create` | map / assoc lookup (LOOK's known O(n) sentinel gap) |
| 6 | `json_parse` | parsing |
| 7 | `json_serialize` | serialization |

Run: `cpp/bench/micro/compare.sh` (LOOK vs Node vs PHP, checksum-verified equivalence). Three
implementations, one per language: `look/run.lk`, `node/run.js`, `php/run.php` — identical logic,
identical integer checksums (a checksum mismatch means the implementations diverged, not a result).

### World 2 — Web runtime → `cpp/bench/` + `cpp/bench/race.sh`

| # | Test | Measures |
| --- | --- | --- |
| 8 | HTTP hello world | raw HTTP + framework dispatch |
| 9 | HTTP JSON (GET + POST JSON) | web runtime + serialization on the request path |
| 10 | Template render (T1 static / T2 dynamic / T3 real: layout+partials+loop+condition+DB+escaping) | template engine (the LookPress-relevant number) |

### World 3 — Real web (HTTP + DB + JSON + auth) → `cpp/bench/dbbench/`

Keep the DB driver and the DB engine separate — a slow query is not a slow language.

| # | Test | Measures |
| --- | --- | --- |
| 11 | `SELECT 1` | connection + protocol + runtime overhead (no DB work) |
| 12 | single-row `SELECT ... WHERE id=?` | driver round-trip |
| 13 | DB JOIN (products×categories×brands) | real app; DB becomes dominant |

### World 4 — Survival & scale (LOOK's characteristic axis)

| # | Test | Measures |
| --- | --- | --- |
| 14 | Endurance: 1M / 10M / 50M / 100M requests, RSS + p99 + errors + OOM + restarts per stage | memory stability over time |
| 15 | Concurrency: c=1k / 5k / 10k / 20k, 60s each, keep-alive **and** non-keep-alive separately | scalability + tail under load |

For tests 14–15, publish keep-alive and non-keep-alive as **separate** columns. LOOK is strong
non-keep-alive; Node is strong keep-alive at low load. Both are shown — "LOOK wins everything" is
less credible than the honest split, and less true.

## Running

```bash
# World 1 — language core (checksum-verified, three languages)
cpp/bench/micro/compare.sh

# World 2/3 — web + DB, in the locked container shape
cpp/bench/race.sh            # hello / JSON / template throughput + tail
# DB apps under cpp/bench/dbbench/{look,node,php}/ — start each, then drive from the load-gen container

# Always: after any engine change, prove correctness BEFORE trusting perf
bash cpp/tests/differential_test.sh build/lk build/lk-fcgi
```

## Baseline & regression discipline

1. Capture a **`LOOK <version>` baseline** row before starting a CPU optimization.
2. After each optimization, re-run the affected world and record the new row next to the old one.
3. A CPU win that does not move this harness did not happen. A throughput win that raises `rps`
   while degrading `p99` is a **bad trade** — the 200µs-flat p99 is LOOK's strongest axis, so
   every web change reports `rps` **and** `p99` together, never one alone.
